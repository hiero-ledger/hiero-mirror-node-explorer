What changed from v2, and why. v2 was drawn before the mirror node's CLPR design was final. v3 keeps only what the five mirror node read endpoints (/channels, /channels/{id}/messages, /channels/{id}/connectors, /configuration, /endpoint-manifest) and the existing accounts, contracts and transactions APIs can supply.
  • Three tabs, not six. Messages and Connectors moved under their Channel (both endpoints require a channel). The Bundles tab and the Endpoint page are gone: the mirror node has no bundle concept and returns only endpoint addresses.
  • No history tabs. The API returns one version at a point in time, so Channel, Connector, Configuration and Manifest pages get a View as of control instead of History lists.
  • Messages are this ledger's outbound queue. Inbound Data is never stored; the Response this ledger generated for it is, and shows how the inbound message turned out. No Direction, Gas, Delivery or "responded" state.
  • Connector pages show current values only. Minimum stake, ban threshold and quota are node-local, so there are no bars, "Near ban" chips or Economics card.
  • Overview is Network Health and Ecosystem. It opens with search (channel ID, connector ID, sendMessage transaction ID, consensus timestamp or peer chain ID), then which networks this ledger is connected to, all-time message totals from the channel counters, and a short list of what needs attention. A transaction ID is matched by its consensus timestamp against each channel, because the mirror node has no transaction-ID lookup (try 0.0.2101@1762842900.555000111). Messages per day and similar trends are not shown: no endpoint provides them.
  • Every view has a URL (the part after #). Press the browser back button to go back.

How each lookup works. A channel ID is one call. A connector ID or a transaction ID is tried against every channel, because the connectors and messages endpoints need a channel: the explorer asks each channel in turn and shows progress. A transaction ID is matched by its consensus timestamp (looked up in the existing transactions API), because the mirror node stores messages by channel and timestamp, not by transaction ID. Overviewchannels

Queueschannels

Outbound backlog = next message ID − 1 − acknowledged through. A backlog that keeps growing while the channel is active suggests the peer has stopped acknowledging.

Peerchannels

What this ledger knows about the other side: the limits the peer asked us to respect, and the peer's endpoints. The peer's service address is not recorded.

Closing Progresschannels

A closing channel accepts no new messages and waits for every outstanding message and response to be delivered. It becomes drained when both sides are empty, then closed.
This ledger's outbound queue for the channel, newest first: data messages its applications sent, the responses it generated for inbound data (one per inbound message dispatched here), and control messages. Inbound data messages themselves are not stored, so they do not appear; the response for each one does.

Showing the 30 days to now, the largest window the server allows.
Reply status is the status on a response message. Replies to is the peer's message ID the response answers: this is how an inbound message's outcome is shown. Acknowledged is computed by the mirror node (the message ID is at or below the channel's acknowledged-through counter); the Acknowledged filter is applied in the browser, as the server filters only by type and connector. Connector is blank on response and control rows. The server requires a time bound on every messages query. Messages that arrived in the same bundle share one timestamp, so a page boundary inside such a group can skip or repeat rows.

Connectorsconnectorsexisting

State is read from the connector record: Pending (registered, not completed), Active, Banned (deleted, no stake recipient) or Deregistered (deleted, with a stake recipient). Balance is the connector contract's balance from the accounts API. The mirror node does not publish the minimum stake, ban threshold or in-flight quota, so no column is shown against a limit.

Verifier on this ledgerchannelsexisting

A verifier is fixed for the life of a channel. Contract and fingerprint are what the mirror node stores. Upgradeability and admin key come from the existing contract APIs and are facts for vetting the channel, not a verdict.

Paired Networkchannelsconfig

The other end of this channel. The chain ID is chosen by whoever created the channel, so it is not evidence that the peer is genuine. The mirror node stores only this ledger's verifier. The peer's verifier contract and service address live on the peer ledger and are not recorded here, so they are not shown.

Trust Anchorchannels

The trust anchor is the verifier's current reference point on the peer (a validator set, a sync-committee period, a block header). Only the current value is shown. To see an earlier one, use View as of at the top of the page.

Running Hasheschannels

Each queue keeps a running hash: SHA-256 of the previous hash and the newest message. Both sides must agree on these for a bundle to be accepted.

Overviewconnectors

The ledger deletes a connector's record on a ban or a deregistration, but the mirror node keeps a soft-deleted row. The page renders from that row. A ban has no stake recipient; a deregistration records one. The ban time is the row's last-changed time, and the bundle that caused it is the CLPR Submit Bundle transaction at that timestamp.

Limitsconnectorsexisting

Spendable balance is the leading indicator of CONNECTOR_UNDERFUNDED; in-flight messages block a clean deregistration, and the link next to the count lists exactly which messages are still unacknowledged. Message volume is counted by the explorer from the Channel's messages. These are current values only: the mirror node does not publish the thresholds they would be compared with.
The channel's messages, filtered to this connector. Only data messages carry a connector, so this lists the messages it authorized.

Overviewmessages

Lifecyclemessages

    States only what the mirror node records. The acknowledgement time is not recorded. This ledger does not record the reply to its own outbound message (HIP-1535 §6.4), so no "response received" step is shown for outbound data.

    Payloadmessages

    Raw bytes, hex only. A control message is shown decoded as key/value pairs. Decoding a data payload needs the target application's ABI; the explorer can offer that when the contract is verified on HashScan and falls back to raw bytes otherwise.
